# ADR-0005: Clean-room формат навыков `ASKILL/1` и граница доверия реестра

- **Дата:** 2026-07-26
- **Статус:** Accepted
- **Шаг:** P2.1 (подшаг P2.1.a), см. `docs/ROADMAP.md`

## Контекст

P2.1 даёт Antigona реестр навыков: агент должен уметь снимать удачную траекторию в
переиспользуемую карточку и подбирать её на будущих задачах. Это создаёт три проблемы, которых
не было ни в P0, ни в P1:

1. **Skill poisoning.** Навык, снятый с траектории, которая касалась untrusted-контента, закрепляет
   инъекцию навсегда: один раз прочитанный вредный текст становится «выученной процедурой».
2. **Навык как вектор исполнения.** Любой формат, допускающий shell-строки, шаблоны, include или
   ссылки на внешние файлы, превращает карточку в обход sandbox/HITL/политики рисков.
3. **Утечка критериев верификации.** Если карточка может нести «как проверить успех», агент
   получает доступ к критериям приёмки — это прямой reward-hacking и нарушение границы ADR-0004.

Дополнительное ограничение — clean-room. В `.venv-worker312` физически присутствуют чужие
реализации навыков (`openhands/sdk/skills/*`, `anthropic/.../skills/*`, `fastmcp/.../skills/*`),
а в окружении есть AGPL-исходники klio-tech. Любое заимствование формата или парсера оттуда
загрязняет происхождение кода Antigona (`docs/THIRD_PARTY_STRATEGY.md`).

## Решение

### 1. Собственный формат `ASKILL/1`, а не YAML-frontmatter + Markdown

Навык хранится в файле `.askill` в формате `ASKILL/1`, нормативно описанном в
`docs/SKILL_FORMAT.md`. Формат не использует ни разделители frontmatter `---`, ни YAML, ни JSON.
Заголовочные директивы начинаются с `%`, секции — `[имя]`, шаги плана нумерованы, аргументы
вводятся строкой `~ key = value`, многострочные значения — `<<` … `>>`, файл завершается
директивой целостности `%end sha256:… bytes=…`.

Обоснование отказа от связки «YAML-frontmatter + Markdown»:

- **Clean-room.** `SKILL.md` с YAML-frontmatter — узнаваемый чужой формат. Собственная грамматика
  снимает вопрос о происхождении и проверяется тестом `tests/unit/test_clean_room_skills.py`.
- **YAML небезопасен по умолчанию.** Теги, якоря/алиасы, merge-ключи, неявные приведения типов
  (`no` → `False`, версии → числа) и раскрытие алиасов дают поверхность атаки и неопределённое
  поведение там, где нужен fail-closed. `ASKILL/1` — line-based грамматика без вложенности,
  без ссылок и без неявных типов.
- **Markdown-тело неверифицируемо.** Проза не даёт детерминированного матчера и не даёт
  побайтовой канонизации. В `ASKILL/1` триггеры — структурные правила (`kw`, `path-prefix`,
  `tool-available`), а проза допустима только в `[intent]` строками `>` и парсером не
  интерпретируется.
- **Целостность.** Формат обязан иметь однозначный канонический вид и хеш тела; произвольный
  Markdown этого не даёт.

### 2. Навык — это данные, а не код

Архитектурный запрет: карточка не содержит исполняемого кода. Плановый шаг — это ссылка на
**зарегистрированный тул** Worker'а плюс типизированные аргументы. Запрещены shell-строки, `eval`,
include, env-переменные, ссылки на внешние файлы и бинарные вложения. Единственная подстановка —
`{{slot:NAME}}` с обязательным объявлением слота в `[slots]`.

Из этого следует: навык — **подсказка плана**, а не обход контроля. Каждый шаг, пришедший из
карточки, проходит ту же политику рисков, тот же HITL и тот же sandbox, что и обычный шаг плана.

### 3. Промоушен в `ACTIVE` — исключительная привилегия Verifier

Жизненный цикл: `DRAFT → CANDIDATE → ACTIVE → DEPRECATED | QUARANTINED | REJECTED`.
Переход `CANDIDATE → ACTIVE` выполняет только Verifier (bearer из `security.verifier_credential()`
плюс CAS по `revision`). Ни Gateway, ни Worker не имеют пути записи статуса `ACTIVE` — это
структурный аналог принятого правила «`DONE` ставит только Verifier».

`QUARANTINED` — sticky-состояние без обратного пути. Любая попытка перехода, включая отклонённую,
пишется в append-only таблицу `skill_transitions` (`accepted=false` + `reason`).

### 4. Реестр остаётся на SQLite

Реестр навыков живёт в SQLite рядом с durable-состоянием. Миграция в PostgreSQL откладывается
до P4 вместе с остальным durable-state: реестр read-mostly, запись редкая, триггеры ранней
миграции (конкуренция нескольких Worker, `SKIP LOCKED`, блокировки) для него не доказаны.
Это продолжение линии ADR-0003, где выделенный PostgreSQL заведён только под память P1.

Тела карточек хранятся контент-адресуемо в файловом хранилище по правилам артефактов P1.3:
каталог `0750`, файлы `0640`, отказ на symlink, отказ при `st_nlink > 1`, отказ при выходе пути
за корень, атомарная запись, обязательная проверка `body_sha256` при каждом чтении. Несовпадение
хеша → `SkillIntegrityError` и автоматический перевод навыка в `QUARANTINED`.

### 5. Наследование trust из P1.3

Навык, снятый с траектории, которая касалась untrusted-контента, наследует метку
`%trust untrusted` и получает жёсткий потолок риска `LOW`. Это прямое продолжение
trust-degradation, принятой в P1.3: untrusted-навык не может повысить потолок риска и не может
активировать сетевые тулы. Захват (`capture`) всегда даёт `DRAFT`; автоматического промоушена нет.

### 6. Clean-room ограничения (обязательны к соблюдению)

- **Запрещено** читать и заимствовать реализации навыков из `.venv-worker312`:
  `openhands/sdk/skills/*`, `anthropic/.../skills/*`, `fastmcp/.../skills/*`. Разрешена только
  публичная идея «навык = переиспользуемая процедура».
- **Запрещено** читать и заимствовать AGPL-код klio-tech (`docs/THIRD_PARTY_STRATEGY.md`).
- Имена, бренды и примеры навыков upstream не заимствуются: все примеры в `examples/skills/`
  пишутся с нуля под задачи Antigona.
- Проверяется тестом `tests/unit/test_clean_room_skills.py` и clean-room аудитом `git log -p` шага.

### 7. Непротиворечие ADR-0004

ADR-0004 закрепил: критерии завершения живут только в `verifier_criteria`, чья mapped-class,
declarative metadata и session factory находятся исключительно в `antigona.verifier.criteria`,
и ни у worker, ни у gateway нет shared-ORM пути к скрытому значению.

`ASKILL/1` эту границу не ослабляет и не дублирует:

- карточка **не содержит и не может содержать** критериев верификации задачи — парсер отвергает
  зарезервированные секции и ключи с кодом `E-CRITERIA` (см. `docs/SKILL_FORMAT.md`);
- секция `[claims]` — это **претензии карточки о её собственном эффекте** (например
  `produces-file`, `no-network`), которые Verifier проверяет детерминированно перед промоушеном.
  Это не критерии приёмки задачи и они не хранятся в `verifier_criteria`;
- проверки промоушена (`verifier/skill_checks.py`) выполняются на стороне Verifier, вне sandbox
  агента, и их результат агенту не раскрывается;
- единственный источник критериев задачи остаётся `VerifierCriteriaStore`.

## Последствия

- Появляется собственная грамматика, парсер, канонизатор и спецификация `docs/SKILL_FORMAT.md`,
  которые нужно поддерживать; цена принята сознательно ради clean-room и fail-closed.
- Fail-closed на неизвестных директивах и секциях плюс правило «новая секция = новая
  major-версия» (`%ASKILL 2` + отдельный ADR) не дают формату расползтись.
- Публичный API `SkillsRegistry` (`save_skill`, `save_from_task`, `get_skill`, `list_skills`)
  сохраняется через фасад `skills/__init__.py`; новые параметры — keyword-only с дефолтами,
  существующий `tests/unit/test_skills.py` проходит без правок.
- Таблица `skills` расширяется, добавляется append-only `skill_transitions`; требуется инкремент
  `schema_version`, детерминированный бэкфилл (`status = DRAFT`) и паритет «SQL-таблицы == ORM
  metadata».
- Gateway получает только read-only `GET /skills`, `GET /skills/{id}`; `promote` проксируется в
  Verifier, поскольку у Gateway нет verifier-креда и нет SQL-пути к `ACTIVE`.
- Семантический/векторный подбор навыков, sharing между owner'ами и cron/replay в границы P2.1
  не входят.
