# Contributing to Antigona

Спасибо за интерес. Ниже — как поставить окружение, что считается готовой
правкой и какие правила процесса обязательны (не «желательны»).

> Правила безопасности — в [`SECURITY.md`](SECURITY.md). Если ваша правка
> затрагивает ограду путей, approvals, песочницу или верификацию — прочитайте
> его до начала работы.

---

## 1. Требования

- **Python 3.11 или новее** (`requires-python = ">=3.11"` в `pyproject.toml`).
- Linux или macOS, bash. Установка **не использует `sudo`** и не пишет вне каталога клона.
- Ничего платного не требуется: базовые зависимости ставятся из PyPI, тесты не
  должны требовать внешних ключей или сервисов.

## 2. Установка окружения

```bash
git clone <URL репозитория, из которого вы работаете>
cd <каталог клона>
bash install.sh --dev        # venv + пакет + extras [dev]: pytest/ruff/mypy
source .venv/bin/activate
```

`install.sh` в конце сам проверяет, что пакет импортируется и CLI запускается;
если проверка не прошла — он возвращает ненулевой код и **не** печатает, что
всё хорошо. Повторный запуск безопасен (идемпотентен). Откат — удалить `.venv/`.

## 3. Четыре гейта (обязательны перед PR)

Это ровно те команды, что и в CI (`.github/workflows/ci.yml`). Запуск всех
сразу:

```bash
bash scripts/ci_local.sh
```

Или по одной:

```bash
ruff check src/ tests/
python3 scripts/arch_guard.py
mypy --strict src/antigona
ulimit -Sn 1024
unset ANTIGONA_PIN
pytest tests --tb=short -q
```

Что означает каждый гейт — в разделе 6 [`ARCHITECTURE.md`](ARCHITECTURE.md).
Полный набор тестов идёт около десяти минут; во время разработки гоняйте
точечно, полный прогон — перед PR:

```bash
pytest tests/unit/test_<ваша_область>.py -q
```

### Запрещено ради «зелёного»

- Поднимать `ulimit`, удалять/скипать тесты, добавлять `xfail` вместо исправления.
- Ослаблять гейты: approval, ограду путей, единый chokepoint инструментов,
  проверку артефактов, sandbox.
- Добавлять новые строки в `scripts/arch_baseline.txt`. Этот файл —
  зафиксированный архитектурный долг, он обязан только сокращаться
  (`scripts/arch_guard.py`, ADR-007).
- Заменять реальную работу заглушкой. Mock/stub разрешён **только** внутри
  явно тестовой зоны; в рабочем пути это дефект.

## 4. Стиль кода

- **Типизация обязательна.** `mypy --strict src/antigona` должен быть чист.
  Публичные функции получают аннотации; для непокрытых внешних модулей есть
  `[[tool.mypy.overrides]]` в `pyproject.toml`.
- **Линтер:** `ruff` с набором `E, F, I, B, UP`, длина строки 100
  (`[tool.ruff]`). Автофикс: `ruff check --fix src/ tests/`.
- **Формат импортов** — как у ruff-isort; сортировку не настраивайте локально.
- **Язык.** Комментарии и docstring — на языке либо русском, либо английском,
  но внутри одного файла держитесь одного стиля. Сообщения для пользователя —
  на русском, без выдуманных деталей вроде версий и дат.
- **Никаких хардкодов путей.** Единственный источник правды о путях —
  `src/antigona/core/paths.py`. `Path.home()`, `expanduser()` и строки вида
  `/home/user/...` вне него запрещены `arch_guard`.
- **Ошибки — fail-closed.** Неизвестное состояние (файл не прочитан, хеш не
  совпал, документ отсутствует) обрабатывается как отказ, а не как «продолжаем».

## 5. Clean-room

Проект — **clean-room реализация**. Запрещено копировать код, UI, бренды,
навыки (skills) или ассеты сторонних проектов, включая AGPL-проекты без
отдельного лицензионного аудита. Идеи — можно, код — нет.

## 6. Секреты и приватность

- Никогда не коммитьте `.env`, `*.pem`, `*.key`, дампы БД, логи сессий, дампы
  переписок, скриншоты с токенами.
- Тесты не должны требовать реальных ключей. Нужен внешний сервис — тест
  обязан корректно скипаться без него, а не падать и не подделывать результат.
- В фикстурах, отчётах и примерах используйте только обезличенные значения.
- Нашли секрет в истории/коде — не «латайте» публично. Сообщите приватно,
  см. [`SECURITY.md`](SECURITY.md).

## 7. Процесс правки

1. **Один писатель на кандидата.** Не редактируйте файл параллельно с кем-то
   ещё; если правка уже идёт — согласуйте разделение.
2. **Ветка на одну тему.** Небольшая правка = небольшая ветка.
3. **Коммиты** — в стиле проекта (`git log --oneline`), префикс области и
   краткое существительное-описание на английском:
   `fix(fence): …`, `feat(chain): …`, `fix(security): …`, `chore(manifest): …`,
   `fix(ci): …`, `docs: …`. В теле — что было не так и почему правка это
   закрывает. Не объявляйте в сообщении то, что не подтверждено проверкой.
4. **Тест на правку.** Исправление бага приходит с регрессионным тестом.
   Новая возможность — с тестом на основной путь и на отказ.
5. **Независимое ревью.** Ревьюер не должен быть автором правки. Для правок в
   безопасности, approvals, ограде путей и песочнице независимое ревью обязательно.
6. **Никаких необратимых действий** (публикация, деплой, удаление данных) без
   явного одобрения владельца. Автоматического одобрения не существует.

## 8. Чеклист перед PR

- [ ] `bash scripts/ci_local.sh` — все четыре гейта `rc=0`.
- [ ] `git diff --check` чист, лишние файлы (кэши, `.venv`, БД, логи) не попали в диф.
- [ ] Новый/изменённый код покрыт тестами; тест воспроизводит баг до правки.
- [ ] Публичные интерфейсы типизированы, `mypy --strict` чист.
- [ ] Никаких секретов, реальных идентификаторов, персональных данных и
      внутренних путей в диффе, тестах и документации.
- [ ] Документация обновлена, если изменилось поведение, команда или файл,
      на который ссылаются README/ARCHITECTURE.
- [ ] Если менялось содержимое кандидата — конверт неизменяемости и манифест
      пересчитаны в рамках процесса, а не «подогнаны» под результат.

## 9. Что приведёт к отклонению PR

- Ослабление или обход гейта безопасности.
- Правка, «проходящая» только на локальной машине автора (захардкоженные пути,
  имена пользователей, наличие незадекларированной зависимости).
- Тест, который всегда зелёный, или тест, подменяющий реальную работу заглушкой.
- Объявление «готово/исправлено» без наблюдаемого доказательства: вывода
  команды, кода возврата, состояния файла.
- Коммит с секретом, чужими персональными данными или скопированным кодом.

## 10. Вопросы

Вопросы по правке — в issue репозитория, где вы работаете. Про уязвимости —
**только** приватным каналом из [`SECURITY.md`](SECURITY.md), не в issue.
