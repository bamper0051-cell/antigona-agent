# Security Policy — Antigona

## Коротко

- **Как сообщить об уязвимости:** приватно, через механизм **GitHub Private
  Vulnerability Reporting** в репозитории, из которого вы получили этот код:
  вкладка **Security** → **Report a vulnerability** (создаётся приватный
  security advisory). Публичный issue с деталями уязвимости создавать нельзя.
- **Если приватный канал недоступен:** создайте **пустой** issue с текстом
  «security: request private channel» и без технических деталей — с вами
  свяжутся для организации приватного канала.
- **Персональных адресов для сообщений об уязвимостях в этом документе нет** —
  мы намеренно не публикуем контактные данные. Не отправляйте отчёты в
  публичные мессенджеры и не прикладывайте рабочие секреты.
- **Поддерживаются:** только `HEAD` ветки по умолчанию. Релизов и тегов,
  объявленных поддерживаемыми, на момент написания этого документа нет.

Это best-effort процесс: у проекта нет коммерческого SLA и дежурной команды.
Мы отвечаем по возможности и не даём сроков, которые не можем выполнить.

## 1. Область действия (in scope)

Проект — автономный агент, исполняющий код и инструменты. Уязвимостью считается
любое **нарушение заявленного инварианта безопасности**, в первую очередь:

| Категория | Что считается уязвимостью |
|---|---|
| Обход ограды рабочей области | Чтение/запись/исполнение **вне** разрешённого workspace: `..`, абсолютные пути, symlink-предки, hardlink, Unicode NFC/NFD-эквиваленты, aliases монтирований, encoded traversal (`%2e%2e`, двойное кодирование) |
| Обход approval | Операция с повышенным риском выполняется без явного одобрения владельца; grant переиспользуется; отказ трактуется как разрешение |
| Обход единого chokepoint инструментов | Инструмент выполняется в обход `engine/unified_executor.py` (`UnifiedToolExecutionLayer`) |
| Побег из песочницы | Выход за пределы изоляции Docker/microVM: сеть там, где заявлен `none`, запись при `read_only`, повышение привилегий при `--cap-drop=ALL` |
| Ложный `DONE` | Задача переводится в `DONE` без проверки артефакта на диске: подделка доказательства, symlink вместо обычного файла, неполное выполнение составной цели как `DONE` |
| Утечка секретов | Ключи/токены/пароли попадают в git, логи, отчёты, трассировки исключений, прогресс-сообщения или артефакты доставки |
| Небезопасный ввод-исполнитель | Ввод, который заставляет агента исполнить то, что политика запрещает (prompt injection → tool execution в обход policy) |
| Утечка внутренних данных наружу | Доставка артефакта/отчёта не тому получателю; отправка наружу без approval |
| Fail-open при неизвестном состоянии | Отсутствующий/нечитаемый конфиг, манифест или документ трактуется как «всё в порядке» вместо отказа |

## 2. Что мы НЕ считаем уязвимостью

- Известные ограничения, честно описанные в документации проекта
  (например, окно at-most-once при доставке, если оно заявлено как известное).
- Работа кода, запущенного **по вашей же команде** на вашей машине с уже
  выданными правами, если это не нарушает инвариант выше.
- Отсутствие фич, DoS «выключил питание», социальная инженерия.
- Находки в сторонних зависимостях без подтверждённого вектора в Antigona —
  сообщайте апстриму; мы примем информацию, но это не наш гейт.
- «Агент сделал то, что я попросил, а результат мне не понравился» — если
  политика и approval были соблюдены, это баг продукта, а не уязвимость.
  Заводите обычный issue.

## 3. Чего НЕ делать при проверке (правила испытаний)

Проект приветствует исследование безопасности, но с жёсткими рамками:

1. **Не выводить секреты наружу.** Если в ходе проверки вы получили токен,
   ключ, чужой файл или персональные данные — остановитесь, не сохраняйте и не
   пересылайте; в отчёте покажите **маскированный** фрагмент (`sk-...a1b2`).
2. **Не разрушать данные.** Никакого удаления/шифрования, никаких атак на
   живые системы третьих лиц. Проверки — на своей изолированной копии.
3. **Не атаковать инфраструктуру.** Никакого спама, brute-force, эксплуатации
   чужих аккаунтов, сканирования чужих сетей.
4. **Не публиковать детали до согласованного раскрытия.** Стандартный порядок:
   приватный отчёт → подтверждение → исправление → и только потом публичное
   раскрытие, если обе стороны согласны. Мы просим **90 дней** тишины или до
   выхода исправления — что наступит раньше.
5. **Не вставлять в отчёт реальные имена, адреса, номера, идентификаторы
   аккаунтов** — обезличивайте.

Соблюдение этих пунктов — условие добросовестности (safe harbor в пределах
нашей юрисдикции и применимого права: мы не будем инициировать претензии по
исследованиям, проведённым по этим правилам).

## 4. Что положить в отчёт

Чем точнее отчёт, тем быстрее разбор. Минимальный набор:

```
1. Что нарушено       — какой инвариант из раздела 1.
2. Версия/ревизия     — вывод: git rev-parse HEAD, git branch --show-current
3. Окружение          — ОС, версия Python, режим (CLI / Telegram / сервисы)
4. Воспроизведение    — точные шаги; минимальный скрипт/команды
5. Наблюдаемый факт   — фактический вывод/состояние на диске (не пересказ)
6. Ожидаемое поведение— что должно было произойти (отказ/fail-closed)
7. Оценка влияния     — что реально может сделать атакующий
8. Приложение         — логи с МАСКИРОВАННЫМИ секретами
```

Отчёт без воспроизведения мы всё равно примем, но разбор займёт больше времени.
Отчёт **с** рабочими секретами мы вынуждены удалить сразу — это правило
безопасности, а не невежливость.

## 5. Что мы делаем дальше

1. Подтверждаем получение (best effort, без SLA).
2. Воспроизводим на канонической ревизии и определяем класс: P0/P1/… .
3. Исправляем по циклу проекта:
   `RED → RCA → минимальное исправление → GREEN → регрессионный тест → независимое ревью`.
   Обязательно добавляется регрессионный тест, иначе исправление не считается
   закрытым.
4. Согласуем раскрытие с вами и, если вы хотите, указываем автора находки.

## 6. Безопасные настройки: что обязан сделать оператор

Проект сам по себе не создаёт секреты и не требует их. Но:

- Ключи храните **только** в переменных окружения или локальном `.env`
  (он в `.gitignore`); никогда — в коде, тестах, issues, скриншотах.
- Никогда не публикуйте `.env`, файлы `*.pem`/`*.key`, дампы БД и логи
  с содержимым задач.
- Запускайте от непривилегированного пользователя. Установщик `install.sh`
  **не использует `sudo`** и пишет только в каталог клона.
- Опасные операции исполняются в песочнице — не отключайте изоляцию ради
  «чтобы работало».
- Approval — это реальный человек в моменте. Автоматическое одобрение
  запрещено устройством системы, а не настройкой.

## 7. Инварианты безопасности проекта (справочно)

Эти правила определяют, что считается багом, а не мнением:

1. Нет доказательства — нет PASS.
2. Нет независимого подтверждения — нет финального `DONE`.
3. Неполное выполнение составной задачи — не `DONE`.
4. Неизвестное состояние побочных эффектов — отказ (fail-closed).
5. Возможность не рекламируется, пока не доказана рабочей.
6. Заглушка допустима только внутри явно тестовой зоны.
7. Один писатель на кандидата.
8. Ревью независимо от автора правки.
9. Старый хеш — не доказательство текущего состояния.
10. Секреты не попадают в архивы и отчёты.
11. Публикация и разрушительные операции — только с одобрения владельца.
12. Несовпадение хеша конституции/манифеста — безопасный режим, а не предупреждение.
13. Отсутствие непрерывности данных — требование восстановления, а не «продолжаем как было».
14. Доставка наружу подтверждается фактом получения, а не статусом «отправлено».
15. Доступность внешнего сервиса — факт, который проверяют, а не предполагают.
